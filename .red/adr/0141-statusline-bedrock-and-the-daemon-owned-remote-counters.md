# 0141 — Statusline bedrock, daemon-owned remote counters, and serve-from-cache-always

The statusline's data was coupled across owners: remote tracker counters (open PRs/issues, `rdy=`/`hmn=` queue counts) were fetched by local `gh` subprocesses under a 15-minute TTL (`STATUSLINE_CACHE_TTL_S = 900`), local git facts rode the same cache file, and the operator could not tell what stood between the line and its data when redskilled was down or the project unregistered. We decided to split the line by data ownership and make the daemon's cache semantics strict.

## Decisions

1. **The Statusline Bedrock is the zero-network, zero-daemon first segment.** Everything that answers locally — the Claude Code stdin payload (model·effort, context tokens/percent, `5h=`/`7d=` subscription windows), local git facts (basename, branch, local diff), and the running bundle version — renders on every invocation regardless of redskilled's state. Local git facts move out of the 15-minute remote-counter cache into a ~5s micro-TTL of their own. The bedrock renders in `apps/dev` (the owner of the stdin contract); the tail keeps coming from the Shared render (ADR 0130 rule 10), which never learns what Claude Code stdin is.
2. **Every remote counter is daemon-owned.** Open-PR/issue counts and the `rdy=`/`hmn=` queue counts move into redskilled's repository-activity polling — one owner, one cycle, one payload — and the statusline's local `gh` count cache dies. The daemon poll is presence-driven: ~15–30s while an interactive session is registered, backing off when the host is idle, always under the budget-aware GitHub client (ADR 0132). The operator's perceived 5-second reactivity comes from the per-render local socket read, not from polling GitHub at 5s.
3. **A request never fetches.** The daemon serves repository data from its cache on every request — MCP tool call or statusline read — with the age stated in the payload. Only the daemon's own poll cycle talks to GitHub. This is the rejection of request-triggered background refresh: a surface asking a question must never be able to spend the GitHub budget or create a fetch storm.
4. **The Statusline Lifecycle is a visible state machine.** `bedrock-only`, `connecting`, `registering`, `unregistered` (daemon up, nothing registering this repo — deliberately distinct from `registering`, which promises progress), `live`, and `degraded`. Non-`live` states render as a compact `rsk=<state>` token in place of the redskilled tail; in `live` no state token renders — the data speaks. The per-render socket read carries a hard ~150ms deadline; a miss serves the last-known tail with its age plus the lifecycle state, so the prompt never freezes (the #3546 lesson) and never amputates silently.
5. **The bedrock/tail seam is the future composability unit.** The layout stays fixed for now; segments are drawn as internal units so operator-composable segment selection can land later without redrawing data ownership.

## Consequences

The statusline becomes honest about three previously invisible situations — daemon down, registration pending, and nobody registering at all — and the 15-minute staleness window on tracker counters collapses to the daemon's presence-driven poll. The cost is that tracker counters are only as fresh as the daemon's cycle: an operator who wants a forced refresh acts on the daemon, not on the reading surface.
