# Pi packages ship on npm as `@reddb-io/red-skills-<plugin>` for one-command install

## Status

Accepted. Records the second-slice Pi integration that turns the path-based install shipped in #2167 into the npm-distributed path a user can reach with `pi install npm:…`.

## Context

PR #2167 added Pi as a fourth host alongside Claude Code, Codex, and OpenCode by generating `plugins/<name>/package.json` per plugin and exposing `scripts/install-pi.sh` to wire them through `pi install <local-path>`. That first slice is correct but **incomplete as the public user path**: it requires the user to clone the red-skills monorepo, run `pnpm install`, and invoke the installer from inside that checkout. A user opening Pi today and asking "how do I get RedSkills?" has no first-class answer; Claude Code and Codex both have one (`/plugin marketplace add reddb-io/red-skills` then `/plugin install dev@red-skills`).

Pi's documented install surface is three forms — `npm:`, `git:`, and local path — and only the first two are "natural" in the sense that the user does not need to know where the source lives. `git:` would require either four repos (one per plugin) or a single monorepo install where every skill from every plugin lands as one undifferentiated package; both shapes fight Pi's per-package identity model. `npm:` lets each plugin be its own package, versioned and discoverable through the existing `@reddb-io` scope already in use for `@reddb-io/red-skills` (the runtime bundle, ADR 0091).

The skill payload itself is tiny: every plugin's `skills/<bucket>/<skill>/SKILL.md` totals a few hundred KB across all four plugins. There is no build step, no native dependency, and no platform split. A pure-data npm package carrying the staged skills plus the generated `pi-package` `package.json` is the simplest distribution that satisfies Pi's recursive-skill discovery.

## Decision

The Pi integration ships on npm as four scoped packages, one per published plugin, under the `@reddb-io` scope:

- `@reddb-io/red-skills-dev` — the `dev` plugin's skills (engineering / knowledge / productivity / misc)
- `@reddb-io/red-skills-memory` — the `memory` plugin's skills (core)
- `@reddb-io/red-skills-brain` — the `brain` plugin's skills (core)
- `@reddb-io/red-skills-internal` — the `internal` plugin's skills (maintainer-only; public npm but gated by `plugins.internal.enabled: true` per ADR 0067, the same way the Claude and Codex marketplaces already expose it)

The end-user path becomes a one-line command per plugin — exactly what Pi's docs advertise as the natural install:

```bash
pi install npm:@reddb-io/red-skills-dev
pi install npm:@reddb-io/red-skills-memory
pi install npm:@reddb-io/red-skills-brain
```

`scripts/install-pi.sh --user` defaults to those four `npm:` URLs; the path-based install from #2167 stays available behind `--source-dir <path>` for in-repo development, smoke testing, and offline use.

Versioning stays unified with the rest of the monorepo (ADR 0040): every release cuts one version, and the generator emits the same version into all four published Pi packages plus the existing `@reddb-io/red-skills` runtime bundle. A user on `v2.75.0` gets matching skills and runtime with a single `pi update --all`.

## What ships

### Packaging layout

```
packaging/pi/
├── dev/
│   ├── package.json           # generated by build-pi-packages.mjs
│   └── skills/                # copied from plugins/dev/skills/<bucket>/
│       ├── engineering/.../SKILL.md
│       └── …
├── memory/
│   ├── package.json
│   └── skills/core/.../SKILL.md
├── brain/
│   ├── package.json
│   └── skills/core/.../SKILL.md
└── internal/
    ├── package.json
    └── skills/maintainer/.../SKILL.md
```

Each `package.json` carries the same shape the #2167 generator already produces (the `pi-package` keyword, the `pi.skills` array with `./skills/<bucket>/` paths, the version inherited from the canonical Claude-side manifest), minus the `"private": true` flag and with `"publishConfig": { "access": "public" }` added. The generator's two outputs diverge only in those two flags plus the destination directory — the rest is byte-for-byte the same.

### Build step

`scripts/build-pi-packages.mjs` (new) is the analogue of `packaging/npm/scripts/prepare.mjs`: it stages the published skill tree from `plugins/<name>/skills/<bucket>/` into `packaging/pi/<name>/skills/<bucket>/`, regenerates each `packaging/pi/<name>/package.json` from the Claude-side manifest, and fails the build when a published bucket is missing on disk or `in-progress/` leaks in. The release pipeline runs it before publish; local development runs it on demand via `pnpm pi:packages:build`.

### Installer change

`scripts/install-pi.sh` flips its default to `pi install npm:@reddb-io/red-skills-<plugin>`. The `--source-dir <path>` flag keeps the path-based install working for the in-repo dev workflow and for the universal `scripts/install.sh`, which already extracts the release into `~/.red-skills/current/` and now passes that path through `--source-dir`. The `--local-source` alias (and the universal installer's invocation contract) keeps the path install available without changing the user-facing one-liner.

The uninstall path stays symmetric: `--uninstall --user` issues `pi remove npm:…` for every recorded package, and the manifest at `~/.pi/agent/redskills-install-manifest.json` records either form so reruns converge.

### Release pipeline

`.github/workflows/red-release.yml` adds one `publish-pi-packages` job that runs after the existing `@reddb-io/red-skills` npm publish:

1. `pnpm pi:packages:build` — stages skills into `packaging/pi/<name>/`.
2. Per plugin, a `pnpm --dir packaging/pi/<name> publish --access public --no-git-checks`, idempotent on `npm view @reddb-io/red-skills-<plugin>@${version}` (matching the existing `@reddb-io/red-skills` idempotence contract).
3. A smoke step that runs `pi install npm:@reddb-io/red-skills-dev@${version}` in a disposable container, asserts the `pi list` output contains the package, then `pi remove`s it. The container reuses the same npm-cache isolation pattern the existing `@reddb-io/red-skills` smoke uses.

### Documentation

`README.md` "Manual: Pi" gets a one-liner-first path (`pi install npm:@reddb-io/red-skills-dev` and friends) with the script-based path demoted to the development section. The Pi Manifest Maintenance section keeps the `pnpm pi:manifests` / `pnpm pi:packages:build` invocations documented because they are the regeneration gate CI runs.

## Why not other shapes

**Single monorepo npm package (`@reddb-io/red-skills-pi` with everything inside).** Rejected: Pi's per-package identity model treats the four plugins as one undifferentiated blob, the `view` skill collision (memory + brain both ship `name: view`) cannot be disambiguated by install order because the operator has no per-plugin toggle, and the user's mental model "install the dev skills, then maybe memory" no longer maps to one command per plugin. The 4×2 KB of metadata overhead is not worth losing granularity.

**Four separate git repositories.** Rejected: monorepo invariants (ADR 0034/0060), shared plugin gates (ADR 0067), and the cross-plugin `ask-red` Coverage Inventory all assume one repo. Splitting would fork the source of truth and lose the path-based dev install as a side effect.

**`pi install git:github.com/reddb-io/red-skills@vX.Y.Z`.** Rejected: Pi treats one git URL as one package; subpath filtering per plugin is not a first-class Pi feature. The user would have to install the monorepo four times into four local directories and reference each one manually. Even with a `pi.packages` filter object in settings, the surface is not the one-line install the docs promise.

**Path-based install as the only public path.** That is the #2167 status quo. Rejected for public users: requires cloning the source monorepo, defeating the "agent should adapt to my workflow" posture (CLAUDE.md rule 1), and gives a maintainer-shape install to end users.

## Trade-offs accepted

- **Skill collision between `memory` and `brain` for `name: view`** is unchanged. Pi warns-on-collision and keeps the first-registered match; the install order is documented in the README (install whichever `view` you want primary last). Renaming one side would touch the Codex/Claude manifests and the marketplace and is out of scope.
- **No native hook surface in Pi** is unchanged. The hooks that ship with Claude/Codex (`rsp` interception, `red-fetch`, `command-guard`, `branch-lock`, statusline wiring) stay inert in Pi; the skills themselves remain navigable, and AFK runners and the code-nav MCP server are unaffected because they are invoked from the skills via the runtime bundle, not from hooks.
- **Internal plugin ships to the public npm registry.** This mirrors how the Claude and Codex marketplaces already expose `internal`; the gate is `plugins.internal.enabled: true` (ADR 0067), not package availability. Operators who do not set the gate simply never load the package's skills.
- **Four publishes per release.** The release pipeline becomes one additional job with a four-step matrix; npm's immutable versions make the publishes idempotent on re-run.
- **Total tarball weight** is dominated by markdown and stays in the tens of KB per package; no bundler cost.

## Consequences

- A user installing RedSkills in Pi runs three `pi install npm:@reddb-io/red-skills-<plugin>` commands (or one universal installer invocation) and gets the same skill set Claude/Codex/OpenCode expose, with auto-update via `pi update --all`.
- The path-based install from #2167 is no longer the canonical user path but remains the canonical dev path; the `--source-dir` flag keeps both surfaces wired through one installer script.
- The release pipeline gains one new publish job and one smoke job. The existing `pnpm pi:manifests` (regenerates `plugins/<name>/package.json`) and the new `pnpm pi:packages:build` (stages `packaging/pi/<name>/`) together cover both surfaces and run in the same `red-release.yml` pre-publish phase.
- Future Pi hooks (extension API for lifecycle events, MCP stdio bridge, etc.) ship as separate ADRs; this ADR commits only to skills via npm.
