An isolated lane can no longer be promoted into the fleet's pool (#2894). `/go` is documented as safe to run beside any fleet, and that promise rested on a single fact: the disposable issue carries `lane:go` and never `ready-for-agent`, so the fleet's candidate listing cannot see it. The mint honoured that; nothing downstream enforced it. The lifecycle model reasoned about parks and blocks and knew nothing of lanes, so a `from: "*"` promote edge could legally land `ready-for-agent` on a lane-isolated issue — and one was observed carrying both. Both pools would then work the same issue in different worktrees on branches with the same name, racing to push and to open a pull request, and the loser's work is the invisible branch this repository has already lost three times.

**`ready-for-agent` and a lane-isolation label are now mutually exclusive, enforced where the label is written rather than where it is minted.** `validateIssueLifecycleTransition` refuses the pairing before any other reconciliation and the refusal names the EDGE that attempted it, not just the label; unlike a malformed label set, this one cannot be shed on the way through, so the applying site leaves the labels untouched instead of falling back to a best-effort park. Most call sites declare only the labels they intend to shed — a retry says `from: [running]`, and the lane never reaches the pure model at all — so the `gh` label port reads the issue's real labels on any promotion and refuses there too, whatever the write's origin. `lane:scout` is covered identically, for the same reason.

**The fleet's candidate listing now excludes lane-isolated issues outright**, so a stale label already sitting on an issue cannot hand one over. Selection is judged against the pool the candidates were listed under: a worker draining `ready-for-agent` never sees an isolated lane, while the `/go` and scout workers list their own lane and still see their own issue.
