`redskilled` ships as a bundled artifact, so the daemon can exist in production (#2842). The host-scoped execution daemon was a complete, tested, wired-in workspace member that declared no bundle step: every other shipped app names its own entry, outfile and asset name and the root bundle run fans out across them, so this one produced nothing and no release carried it. That is the whole reason the daemon could not run in production by any path — a Worker reaches the runtime through a published bundle, and an app absent from the bundle set is unreachable there however complete its source is. `apps/redskilled` now declares `bundle` on the same pattern (`src/cli.ts` → `dist/redskilled.bundle.min.mjs`, minified), the artifact is staged into the npm tarball behind a `red-skills-redskilled` bin, and the publish workflow builds it, checks the packed tarball carries it, starts the packaged daemon to prove it binds its session socket, and lists it in both the release manifest and the GitHub Release assets. The auto-spawn's default entry no longer guesses a sibling `cli.js` that a bundle never ships (same defect class as #2736): it resolves the named artifact, and treats this module as the entry only when this module IS the artifact, so a foreign host that inlines the client cannot re-exec itself with `serve`. The absence used to be silent; `apps/redskilled/tests/shipped-artifact.test.ts` now fails loudly on any of it — a missing bundle script, an unstaged tarball entry, a dropped release-manifest asset, or an artifact that loads but does not serve. Delivery only: no daemon behaviour changed, and no worker-directory migration happens here.
