The daemon can be asked to stop, instead of being signalled (#2919). `redskilled` exposed no way to leave: replacing a running daemon meant finding its pid and sending `SIGTERM` by hand, which is what had to be done to move a host between two versions. A hand-sent signal ends the same process and can do nothing else — it cannot say what the daemon was holding, cannot be declined, and leaves the successor unable to tell a planned handover from a death, because a lane that simply ends looks identical either way.

**`redskilled stop` is that ask.** It reports the Workers and the projects the daemon is holding and states that every one of them survives — a Worker is an init-system unit and the unisolated fallback is launched detached, so a stop is a restart and never an evacuation. The report is built from the daemon's own facts *before* anything is released, so it describes the machine the operator is about to change rather than the one left over afterwards, and the same report is what the `shutdown` op now answers with instead of a bare acknowledgement. `--reason "..."` carries the operator's own words. Stopping a machine with no daemon on it is a success with a stated reason and never spawns the very process it was asked to remove: the operator asked for a host with no daemon and that is the host they have.

**The stop is written to the host event lane, and named.** `daemon-stop` joins birth, death and budget-kill as the one event that is not about a Worker, carrying a structural `reason` — `requested`, `signal`, `idle`, `replaced` — beside the sentence, so a successor decides what it is taking over from without parsing prose. Every route to a stop records exactly once, and the departure reaches disk *before* the caller is told, so an operator holding a stop report and a successor replaying the lane can never disagree about whether the previous daemon left on purpose. A replay reads the event and retires nothing: the Workers it named are still running, which is precisely what the successor is looking for.
