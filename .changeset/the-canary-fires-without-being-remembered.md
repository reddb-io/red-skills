The MCP lane canary now runs without anyone remembering to run it, and names the socket when the lane fails to cross it (#2844). The canary already knew how to tell an inert lane from an absent worker; what it lacked was delivery — it existed as a command someone would have to type, which is how the daemon subsystem reached a closed Spec with twenty delivered slices, no running process, and no signal at all. The `red-mcp-lane-canary` workflow walks the lane daily, on every push that touches it, and on demand: against the shipped `castle-mcp` bundle with a live `redskilled` daemon, and against two deliberately broken lanes — a slot entry that cannot route `run`, and a session whose daemon socket is dead — that must come back red, so the green is evidence rather than an assumption. It is deliberately not a pull-request gate, because a probe that blocks merges on an unrelated transient becomes one people route around. Both `daemon_reach` failures — a daemon that did not answer, and a vitals row published with no `daemon_liveness` block at all — now name the session socket path, so an operator reading a red canary can tell "restart the daemon" from "fix the lane that stopped asking it"; an unresolvable path reads as `(path unresolved)` rather than as no boundary. `scripts/test-mcp-lane-canary-schedule.sh` holds the schedule and the not-a-gate posture in place in CI.
