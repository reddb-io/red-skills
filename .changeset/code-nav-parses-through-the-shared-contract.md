`code-nav` parses its arguments through the shared contract, and answers `--version` and `--help` before anything else (#2876). The binary branched on `process.argv[2]` in its entry module — three string comparisons deciding whether to print a version or start an MCP server — and had no help surface at all. Every hand-rolled parser has its own answer to the questions a parser must answer: what counts as a flag, what happens to an unknown one, whether `-v` is version or verbose, whether the command may be omitted. Those answers differed per binary, which is why `--version` existed on some shipped binaries and not others — nothing guaranteed it, so each author decided separately.

**Routing and flags now go through `@reddb-io/shared/args`, and the accepted surface is declared rather than walked.** `src/cli-args.ts` states the schema; `routeCommand` peels the (optional) `serve` verb, keeps the `version` command the old branching accepted, and rejects a typo'd one; `parseFlags` handles the long, short, and inline spellings the same way every other RedSkills binary does. `--version`/`-v` print the build version and `--json` prints the structured build info; `--help`/`-h` print usage from the same declaration; an undeclared flag exits 2 with `unknown flag '--bogus'` instead of being silently swallowed into a default the caller believed they had overridden.

**The version answer no longer depends on the thing it is used to diagnose.** The language-server registry, the session map, and the five tool registrations ran at import time, so `--version` loaded the registry before it printed. They now live inside `createNavigator()`, called only on the `serve` path — because "which build is this?" is asked exactly when the box has no language server installed, or a `CODE_NAV_SERVERS` override will not parse, or the MCP host never connected its transport. The suite spawns the binary rather than reading it: that is how the gap was found in the first place, since importing a version helper is not exposing it.
